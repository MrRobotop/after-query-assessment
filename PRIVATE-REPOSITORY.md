# Private repository I would bring

I would bring a private TypeScript and React application for managing a product catalog and viewing brand dashboards, portfolios, and wallet summaries. It uses Supabase for authentication and persisted application data, with SQL migrations and server functions in the same repository. The repository dates to July 2025, about 16 months as of November 2026. Its default branch has roughly 700 tracked files, including about 430 TypeScript and TSX files and 33 SQL files.

I would start with a migration for browser-persisted dashboard data. The codebase already has an auth provider, browser-persisted catalog state, and a wallet summary derived from catalog data and seeded balances. I would use synthetic accounts to investigate whether a cached summary can carry across account switches, particularly when an update from another tab arrives during session restoration. This is a proposed task grounded in the existing code paths. I would qualify it by reproducing the behavior on a pinned revision and checking the intended ownership of each persisted value before writing the prompt.

The verifier would seed distinguishable catalogs and summaries for two accounts, then drive login, sign-out, a second login, and a delayed cross-tab update through the application. It would check the visible summary at those boundaries and after a reload. Same-account reloads would also need to retain their valid cached summaries, so clearing all persisted state on every navigation would fail. I would supply an isolated checkout and scrubbed fixtures for a scored run, subject to the repository’s access terms.

I rechecked the counts directly from GitHub’s recursive tree for the default branch. The response was complete and contained 709 file entries, 433 paths ending in `.ts` or `.tsx`, and 33 ending in `.sql`. For the task idea, I traced three paths in the private source: the auth provider updates the active session, the catalog store subscribes to browser storage events, and the wallet summary reads a browser cache at startup and recomputes on catalog changes. The wallet view also has a loading gate, so reading a cached value in the hook alone does not establish that a user sees stale data. A browser replay with synthetic accounts would determine whether this is a regression to fix or a migration to design.
